# 기능별 테스트 결과 (2026-11-12)

테스트 환경: Linux 컨테이너, Node 22, Chromium(Playwright, 헤드리스), WebKitGTK 2.52(Tauri 데스크톱 WebView, Xvfb).
Windows·macOS 실기기와 iPhone/Android 실기기 테스트는 **아직 하지 않았습니다**(아래 "미검증 항목" 참고).

재현 방법: `./tests/make-audio.sh` → `npm test` → `npm run build && npm run preview` → `npm run test:e2e`

## 1. 테스트 음원
저작권 문제 없이 정답을 정확히 알 수 있도록 **정답(BPM·박자·Key·코드·비트 위치)이 알려진 곡을 합성**해 사용했습니다 (`tests/synth.ts`, `tests/cases.ts`). 킥·스네어·하이햇, 베이스, 배음이 있는 기타형 스트럼으로 구성되며, 4곡은 실제 녹음 조건을 흉내 내기 위해 **튜닝 편차(+35센트, −20센트, A=432Hz)**, 코드 밖의 음을 포함한 **멜로디(보컬 대용)**, **잡음**을 섞었습니다.

> 한계: 합성 음원은 실제 상업 음원보다 깨끗합니다(보컬, 리버브, 디스토션 기타, 믹싱이 없음). 실제 곡에서의 정확도는 이보다 낮을 수 있으며, 정답이 알려진 실제 음원으로 추가 검증이 필요합니다.

## 3. 클릭과 원곡의 싱크
측정 방법: 광대역 "틱"이 0.6초(100 BPM)마다 있는 음원을 앱이 분석 → 메트로놈 ON → **앱의 실제 오디오 출력을 녹음** → 원곡 틱(고역)과 클릭(1320/1760Hz)의 시작 시각 차이를 측정.

초기 구현은 배속 시 15~33ms 어긋났으며, 원인(타임 스트레치 출력의 원곡 위치 계산이 탐색 오프셋을 반영하지 않음)을 찾아 수정했습니다. WebKit 첫 실행 1회에서 0.7배/1.5배 클릭 어긋남이 관찰되었으나, 데이터 초기화 후 포함 3회 재실행에서는 재현되지 않았습니다. 실제 Mac 에서 재확인이 필요합니다.

## 4-1. 악기 강조 (음역대·좌우 위치 방식, AI 없음)
**합성 스템 측정** (`tests/focus.test.ts`): 베이스·보컬·기타(좌우 더블)·건반·드럼을 따로 합성해 각각 필터에 통과시킨 뒤, "대상 악기 음량 변화 − 다른 악기 평균 음량 변화"를 측정 (세기 80%).

| 모드 | 다른 악기 평균 대비 | 가장 가까운 악기 대비 |
|---|---|---|
| 베이스 | +8.2dB | +3.2dB (드럼 킥) |
| 보컬 | +6.8dB | +1.9dB (건반) |
| 기타 | +9.7dB | +3.7dB (보컬) |
| 건반 | +4.5dB | **−1.4dB** (보컬이 더 커짐) |
| 드럼 | +7.1dB | +0.5dB (베이스) |

**실제 앱(Chromium)**: 하단 버튼을 실제로 눌러 앱 출력을 녹음 (멜로디·잡음 포함 테스트곡). 베이스 → 저역/나머지 비 +3.2dB, 드럼 → 고역(심벌) 비중 3.5%→10.4%, 보컬 → 저역 52%→7%·중역 44%→88%, 원음 → 원래 음량의 99.8%. 큰 입력에서도 클리핑 없음(피크 0.98 이하).
한계: 실제 분리가 아니므로 같은 음역대 악기는 함께 커집니다. 특히 건반은 기타·보컬과 구분되지 않을 수 있습니다. 실제 음원에서의 체감은 아직 확인하지 않았습니다.

## 4-2. YouTube 탭 (`tests/e2e/youtube.mjs`, `tests/youtube.test.ts`)
테스트 환경에서 youtube.com 에 접속할 수 없어 **같은 인터페이스의 가짜 플레이어**로 검증했습니다(재생 위치 보고에 ±15ms 지터·50ms 갱신 간격 적용). 실제 YouTube 에서의 동작·정확도는 아직 확인하지 않았습니다.
- 링크 해석 16/16 (watch, youtu.be, shorts, embed, live, 모바일, music, t= 시작 시각, 잘못된 링크 거부)
- 다른 탭에서는 YouTube 접속 0건, 링크 불러오기, 재생, 배속, A-B 반복(구간 유지), 탭 템포(119.9 BPM), 재실행 후 저장 목록·메모 유지, 모바일 390px, 콘솔 오류 없음
- 클릭 예약 오차(가짜 플레이어 기준): 1× 평균 1.0/최대 3.5ms, 0.75× −0.4/4.9ms, 0.5× −3.3/13.1ms, 1.5× −0.9/2.2ms

드럼 강조 수정 후 실제 앱 측정: 고역(심벌) 비중 3.5%→8.1%, 저역 비중 52.5%→36.2%(이전 버전은 저음이 과하게 커짐).

## 5. 긴 파일
약 20분 51초 MP3(192kbps): 디코딩 3.2초, 분석 17.8초, 분석 중 메인 스레드 지연 0ms(UI 멈춤 없음), 끝부분 재생·클릭 정상, JS 힙 약 242MB.

## 6. WebKit (Tauri 데스크톱 WebView, Linux WebKitGTK)
AudioWorklet 동작, MP3/FLAC/OGG/WAV 디코딩·분석 정답, 클릭 싱크 위 표 참고.
M4A 는 **이 테스트 컨테이너의 GStreamer 에 AAC 디코더가 없어** 실패했고, 앱은 이해하기 쉬운 오류 메시지를 표시했습니다. Linux 패키지에는 `gstreamer1.0-libav` 의존성을 추가했습니다. macOS/iOS WebKit 은 시스템 AAC 디코더를 사용하므로 이 문제와 무관하지만 실기기 확인이 필요합니다.

## 7. 데스크톱 빌드
- Linux 에서 `tauri build` 성공(.deb 1.8MB), Xvfb 에서 실행 확인.
- Windows `.exe`(NSIS, 바탕화면·시작 메뉴 바로가기) / macOS `.dmg` 는 해당 OS 가 필요하여 **아직 빌드하지 않았습니다**. GitHub Actions 워크플로(`.github/workflows/build.yml`)를 준비했습니다.
